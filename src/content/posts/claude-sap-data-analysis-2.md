[1편](/posts/claude-sap-data-analysis-1/)에서 클로드를 S/4HANA에 연결하는 네 단계를 적었습니다. 데이터 고르기, MCP 서버 만들기, 배포하고 로그인 붙이기, 커넥터 추가하기. 이 가운데 가장 짧게 넘어갔지만 실제로는 시간이 가장 많이 든 것이 2단계와 3단계, **MCP 서버를 만들고 로그인을 붙이는 일**입니다.

해 보고 나서 든 생각은 이렇습니다. 클로드가 SAP 데이터를 잘 읽느냐 못 읽느냐는 모델보다 **서버를 어떻게 설계했느냐**에 훨씬 크게 달려 있었습니다. 같은 클로드라도 도구가 엉성하면 엉뚱한 숫자를 그럴듯하게 설명하고, 도구가 잘 짜여 있으면 묻는 대로 정확히 가져옵니다. 이 글은 그 설계에서 배운 것을 정리한 것입니다. 코드보다는 "무엇을 정해야 하는가"에 집중했습니다.

## 한 줄 요약

**도구는 질문 단위로, 집계는 서버에서, 권한은 ERP에서, 그리고 응답에는 "실제로 무엇을 조회했는지"를 함께.** 이 네 가지만 지켜도 대부분의 문제가 생기기 전에 막힙니다.

## 시작 전에 — 이 길을 직접 만들어도 되는가

먼저 짚고 갈 것이 있습니다. [지난 데이터 연계 글](/posts/sap-odp-rfc-block-2026/)에서 적었듯이, SAP API Policy는 AI 에이전트가 SAP API를 이리저리 부르는 구성과 프록시·게이트웨이 같은 우회를 문제 삼을 수 있습니다. SAP가 지금까지 예로 든 승인 경로는 Joule 같은 SAP 에이전트, SAP Integration Suite를 거치는 MCP, BDC 정도입니다.

이 연재의 구성은 **테스트 환경에서 직접 붙여 본 기록**입니다. 분석용 CDS 뷰를 OData로 읽는 서버를 직접 만들었지만, 같은 구성을 운영 환경에 그대로 가져가기 전에는 우리 계약과 API Policy에 비춰 SAP에 서면으로 확인하는 것이 먼저입니다. 아래 내용은 어느 길로 MCP 서버를 두든 똑같이 필요한 설계 이야기입니다.

## 1. 도구는 테이블이 아니라 질문 단위로

처음 떠오르는 설계는 "CDS 뷰 하나에 도구 하나"입니다. 뷰 이름을 도구로 노출하고, 클로드가 알아서 필드를 골라 조회하게 하는 방식이죠. 이렇게 하면 도구는 빨리 만들어지지만 클로드가 할 일이 너무 많아집니다. 어떤 뷰에 무엇이 있는지, 어떤 필드를 묶어야 하는지, 금액은 어떤 통화 기준인지를 매번 추측해야 합니다.

그래서 처음부터 도구를 **질문 단위**로 만들었습니다. "운전자본 조회", "채권 연령 분석", "구매처 집중도"처럼 현업이 실제로 묻는 질문 하나에 도구 하나입니다. 도구 안에서 어느 뷰를 어떻게 읽을지는 서버가 정합니다.

도구 설명은 클로드가 읽는 유일한 사용 설명서입니다. 설명에는 네 가지를 적어 두기를 권합니다.

- **언제 쓰는가** — "90일 넘은 채권, 연령 구간별 금액을 물을 때"처럼 질문의 모양으로
- **받는 조건** — 회사, 기간, 거래처 등. 필수인지 선택인지, 형식은 무엇인지
- **돌려주는 것** — 어떤 단위로 묶인 결과인지, 금액의 통화 기준은 무엇인지
- **하면 안 되는 해석** — "기간 증감이므로 시점 잔액처럼 말하지 말 것" 같은 것

설명이 분명할수록 클로드는 도구를 정확히 고르고, 조건도 빠뜨리지 않고 채웁니다. 설명이 모호하면 비슷한 도구 두 개 사이에서 헤매거나, 필요한 조건 없이 도구를 부릅니다.

## 2. 집계는 서버가, 해석은 클로드가

1편에서 "안 되는 질문"으로 적은 것이 원시 데이터를 잔뜩 받아 클로드에게 합계를 맡기는 경우였습니다. 초기 도구 하나가 집계 없이 전표 행을 그대로 돌려줬는데, 행이 많아지자 계산이 흔들리고 답이 느려졌습니다.

원칙은 단순합니다. **서버에서 먼저 묶어서 돌려준다.** 거래처별, 월별, 연령 구간별처럼 질문이 요구하는 단위로 집계해서 보내면 응답이 작아지고 숫자도 안정됩니다. 클로드는 그 결과를 비교하고, 이유를 짚고, 설명하는 데 집중합니다. 언어 모델은 해석에 강하고 대량 합산에 약하니, 각자 잘하는 일을 맡기는 셈입니다.

## 3. 응답에 "실제로 적용된 범위"를 같이 돌려주기

1편에서 적은 **기본값의 함정**은 서버 설계 문제입니다. 회사나 기간을 말하지 않으면 서버 설정의 기본값으로 조용히 조회하는 도구가 있었고, 사용자는 전체를 물었다고 생각하는데 실제로는 일부만 본 셈이었습니다.

고친 방법은 두 가지입니다.

- **응답에 실제로 적용된 조건을 함께 담습니다.** 어느 회사, 어느 기간, 어떤 권한 범위로 조회했는지. 클로드는 이것을 보고 답을 시작할 때 범위부터 말합니다.
- **기본값을 몰래 채우지 않습니다.** 기간을 말하지 않으면 임의로 정하지 않고, 전체 기간으로 조회했다고 밝히거나 되묻습니다. 꼭 필요한 값(예: 특정 거래처)이 없으면 실행하지 않고 그 값을 먼저 묻습니다.

이 장치는 3편에서 다룰 질의 카탈로그에서도 그대로 쓰입니다. "무엇을 조회했는지 보여주는 것"이 결국 숫자를 믿게 만드는 가장 싼 방법이었습니다.

## 4. 권한은 ERP가 판단하게

연결 계정 하나에 넓은 권한을 주고 서버가 알아서 걸러 주는 구성은 만들기 쉽지만 위험합니다. 누가 물어도 같은 범위가 보이고, 서버에 버그가 하나 있으면 볼 수 없는 데이터가 그대로 나갑니다.

그래서 **로그인한 사람의 신원이 ERP까지 이어지게** 했습니다. 클로드에 로그인한 사람의 권한으로 S/4HANA가 조회하고, 볼 수 있는 범위는 ERP의 데이터 권한(CDS 접근 제어)이 판단합니다. 여기에 서버 쪽에 별도 인가 규칙을 두고, **ERP 권한과 서버 규칙 가운데 더 좁은 쪽**이 적용되도록 했습니다. 거래처명 같은 식별자는 정책에 따라 가려서 돌려줍니다.

신원을 이어 주는 방식과 끊기기 쉬운 지점은 [AI가 ERP를 조회할 때, 사용자 권한은 어떻게 지켜질까?](https://blog.aspn.co.kr/ai-agent-erp-user-authorization)에 자세히 적었습니다.

## 5. 로그인 붙이기 — 가장 오래 막힌 곳

클로드의 사용자 지정 커넥터는 공개 인터넷에서 닿는 MCP 서버에 OAuth로 로그인해서 붙습니다. 서버는 SAP BTP에 올렸고, 여기서 1편에 적은 세 가지에 걸렸습니다. 조금 더 풀어 적으면 이렇습니다.

**인증 서버를 찾지 못하는 문제.** MCP 규격에서는 클라이언트(클로드)가 MCP 서버에 처음 붙을 때, 정해진 표준 경로의 메타데이터를 읽어 "어느 인증 서버로 로그인해야 하는지"를 알아냅니다. 그런데 우리가 쓴 인증 서비스가 클로드가 찾는 경로에 응답하지 않아 연결이 거기서 멈췄습니다. MCP 서버가 인증 서버 정보를 대신 알려 주도록 바꿔 해결했습니다. 인증 서비스를 고르기 전에 **MCP 규격이 요구하는 메타데이터 경로를 그 서비스가 제공하는지**부터 확인하면 시간을 많이 아낄 수 있습니다.

**로그인 경로가 여러 개인 문제.** 로그인 화면에 고를 수 있는 로그인 경로가 여러 개 떴는데, **ERP와 신뢰가 맺어진 경로로 로그인해야만** 내 권한으로 조회가 됐습니다. 다른 경로로 로그인하면 로그인은 되는데 내 권한으로 조회가 되지 않았습니다. 사용자가 헷갈리지 않게 경로를 하나로 고정하거나, 적어도 어느 쪽을 골라야 하는지 안내해야 합니다.

**한 시간 뒤 갑자기 끊기는 문제.** 로그인 토큰은 한 시간 정도면 만료됩니다. 갱신 토큰을 켜 두지 않으면 대화 도중에 갑자기 조회가 실패하고, 사용자는 왜 안 되는지 알 수 없습니다. 갱신 토큰 발급, 갱신 실패 시 다시 로그인하라는 분명한 오류 메시지, 둘 다 챙겨야 합니다.

## 6. 기록 남기기

누가, 언제, 어떤 도구로, 어떤 조건으로 조회했는지를 도구 호출 단위로 남겼습니다. 사고가 났을 때 추적하는 용도이기도 하지만, **"어제는 이 숫자였는데 오늘은 왜 다르지?"** 에 답할 때도 쓸모가 있습니다. 같은 도구를 같은 조건으로 다시 부를 수 있으니 결과를 재현할 수 있습니다. 운영 단계에서 필요한 자격증명 교체·감사 로그·가림 처리는 [AI PoC는 성공했는데, 왜 운영 단계에서 막힐까?](https://blog.aspn.co.kr/mcp-server-operations-credentials-audit-masking)에 정리했습니다.

## 시험하는 법

만들고 나서 꼭 해 볼 시험입니다.

- **권한이 다른 두 사용자로** 같은 질문을 던져 결과가 다르게 나오는지 봅니다. 같게 나오면 신원이 ERP까지 안 이어지고 있다는 뜻입니다.
- **기존 보고서와 숫자를 나란히** 대조합니다. 처음 몇 주는 빠뜨리지 않습니다.
- **조건을 빼고 물어** 봅니다. 회사나 기간 없이 물었을 때 서버가 무엇을 했는지, 응답에 범위가 적혀 오는지 확인합니다.
- **한 시간 넘게 대화를 이어** 봅니다. 토큰 갱신이 제대로 되는지 확인합니다.

## 시작 전 체크리스트

- [ ] 이 구성이 우리 계약과 SAP API Policy에 맞는지 SAP에 확인했는가
- [ ] 도구가 테이블이 아니라 질문 단위로 나뉘어 있는가
- [ ] 도구 설명에 언제 쓰는지·받는 조건·돌려주는 것·하면 안 되는 해석이 적혀 있는가
- [ ] 서버가 집계한 결과를 돌려주는가, 행이 잘리면 잘렸다고 알리는가
- [ ] 응답에 실제 적용된 회사·기간·권한 범위가 담기는가
- [ ] 기본값을 몰래 채우지 않고, 필요한 값이 없으면 되묻는가
- [ ] 로그인한 사람의 권한으로 ERP가 조회하는가 (권한이 다른 두 사용자로 시험)
- [ ] 인증 서비스가 MCP 규격의 메타데이터 경로를 제공하는가
- [ ] 갱신 토큰이 켜져 있고, 갱신 실패 시 안내가 분명한가
- [ ] 도구 호출 단위로 기록이 남는가

다음 글에서는 이렇게 만든 서버 위에서 생긴 다음 문제, **같은 질문에 매번 답이 다르게 나오는 문제**를 질의 카탈로그로 어떻게 풀었는지 다룹니다.
